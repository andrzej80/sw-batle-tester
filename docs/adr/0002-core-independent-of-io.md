# 0002. Core не зависит от IO: доменные события и адаптеры в App

Статус: принято (T01, T12–T14).

## Контекст

Формат команд и событий зафиксирован заданием, и код парсера и `EventLog` уже есть в
`IO`. Core — ядро правил, которым будут пользоваться и тесты, и, возможно, другие
приёмники событий. Features публикуют собственные события (например, будущий
`UnitHealed`).

## Решение

- Core объявляет доменные события (`Core/Events/CoreEvents`) и публикует их через
  типизированный `EventBus`. Core ничего не знает о строковых командах и формате вывода.
- Features знают только Core. Параметры юнита фича описывает на своём языке
  (`HunterSpec`) и сама их проверяет.
- Все связи между слоями — в App, отдельным адаптером на команду или событие:
  `App/Bindings` переводит `io::`-команду в вызов Core или фабрики юнита, `App/Output`
  переводит доменное событие в `io::`-событие для `EventLog`. Адаптер — несколько строк
  без логики.
- Границы проверяет сборка: `cmake/CheckLayerBoundaries.cmake` падает со списком всех
  запрещённых `#include`.

## Рассмотренные варианты

- **Core пишет `io::`-события напрямую.** Кода меньше на один адаптер на событие.
  Отклонено: Core зависел бы от формата вывода, а тесты Core — от `EventLog`.
- **DTO команд перенести из IO в App.** Отклонено: App зависит от Features, и фичам
  пришлось бы включать App — получился бы цикл. DTO остаются в IO: это и есть формат
  ввода.

## Последствия

- Каждое событие описано дважды, доменной структурой и `io::`-структурой, а между
  ними стоит адаптер.
- Новый юнит затрагивает Features (конфигурация), IO (команда `SPAWN_*`) и App
  (привязка), но не Core.
- Проверка границ текстовая и не видит включений через макрос (KNOWN_ISSUES, п. 10).
