# 0008. Сценарий проверяется целиком до запуска

Статус: принято (T08, T12, T15).

## Контекст

Сценарий пишут руками, чтобы проверить игровую механику. Если ошибка в девятой строке
обнаруживается только после того, как первые восемь уже напечатали события, лог
получается наполовину настоящим. А если программа падает на первой ошибке, остальные
приходится искать по одной за запуск.

## Решение

Сценарий проходит два прохода:

1. **Проверка.** Все шаги выполняются на отдельном мире без вывода событий. Каждый
   обработчик возвращает `Result`, ошибки собираются: код с пространством имён
   (`unit.duplicate_id`, `hunter.invalid_range`) и сообщение. Файл, номер строки и имя
   команды к ошибке добавляет App.
2. **Итог.** Если есть ошибки, полный список уходит в stderr, stdout остаётся пустым,
   код выхода 2. Если ошибок нет, мир строится заново теми же шагами, уже с выводом
   событий, и запускается симуляция.

Ошибки-последствия подавляются. Например, `MARCH` для отклонённого спавна ошибок не
даёт: первопричина уже в списке.

## Рассмотренные варианты

- **Выполнять по мере чтения и падать на первой ошибке**, как исходный код. Отклонено:
  частичный лог в stdout и одна ошибка за запуск.
- **Один проход с буферизацией событий.** Отклонено: кода больше. Установка не
  использует случайность, поэтому повторить шаги проще, и оба прохода дают одинаковый мир.

## Последствия

- На ошибки пользовательского ввода код не бросает исключения. `std::logic_error`
  означает только баг, это код выхода 3.
- Фичи добавляют свои коды ошибок, не трогая Core: коды — строки, а не общий enum.
- Каталог кодов и формат вывода — ARCHITECTURE.md, п. 6; поведение — SPECIFICATION.md,
  п. 7 и 10.
