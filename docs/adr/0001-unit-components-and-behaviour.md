# 0001. Юнит — набор компонентов и список действий по приоритету

Статус: принято (T04, T10–T11).

## Контекст

Юниты различаются характеристиками и действиями. Одно и то же действие встречается у
разных юнитов с разными параметрами: ближний удар у Мечника бьёт на `Strength`, у
Ворона — на `Agility`. Свойства сочетаются произвольно: Ворон летает, не занимает
клетку, неуязвим для ближнего боя и сам бьёт в ближнем бою. По заданию за ход юнит
выполняет одно действие, юниты ходят в порядке создания.

## Решение

Тип юнита — конфигурация, а не подкласс. `UnitBlueprint` состоит из:

- компонентов: характеристики и состояние, по одному компоненту каждого типа
  (`ComponentStore`, доступ по типу: `get<T>`, `tryGet<T>`, `has<T>`);
- `Behaviour` — упорядоченного списка `IAction`. За ход выполняется первое действие,
  которое вернуло `true`.

Действия параметризуются, а не копируются: `MeleeAttack(stat<Strength>)` и
`MeleeAttack(stat<Agility>)` — один класс. Юнит собирает `UnitBuilder` в Features.
Каждое действие объявляет компоненты, которые читает, и юнит без них не соберётся
(`ComponentRequirements`).

## Рассмотренные варианты

- **Наследование: `Swordsman : Unit` с переопределённым `act()` и виртуальные хуки в
  базовом `Unit`.** Для двух юнитов это проще. Отклонено: каждое новое свойство («не
  занимает клетку», «неуязвим», «нет HP») становится методом базового класса в Core, и
  его владелец превращается в узкое место. Ближний бой Мечника, Охотника и Ворона
  пришлось бы копировать или уводить в глубокую иерархию.
- **ECS: системы, которые обрабатывают компоненты.** Отклонено: правило «одно действие
  за ход, по порядку создания, первое подходящее» всё равно требует выбирать действие
  для каждого юнита по очереди. Получается та же схема, только с лишней церемонией.
- **Характеристики в словаре «строка → число».** Отклонено: опечатку в имени
  характеристики ловил бы тест, а не компилятор.

## Последствия

- Новый юнит — новая конфигурация в `Features/Units`, Core не меняется.
- Порядок «сначала бить, потом идти» — порядок действий в списке, а не код.
- Поведение юнита читается по списку действий, а не по одному методу.
- Ошибку сборки («действию нужен `Strength`, а его нет») ловит не компилятор, а
  создание юнита. Но это происходит на этапе установки сценария, а не на 500-м тике.
