# Архитектурные решения (ADR)

Каждый файл — одно решение: контекст, что решили, какие варианты рассматривали и
почему отклонили, чем за это платим. Устройство целиком — в
[ARCHITECTURE.md](../../ARCHITECTURE.md), известные недостатки — в
[KNOWN_ISSUES.md](../../KNOWN_ISSUES.md).

| № | Решение |
|---|---|
| [0001](0001-unit-components-and-behaviour.md) | Юнит — набор компонентов и список действий по приоритету, а не подкласс |
| [0002](0002-core-independent-of-io.md) | Core не зависит от IO: доменные события и адаптеры в App |
| [0003](0003-unit-died-immediately.md) | `UNIT_DIED` сразу после удара, мёртвый не действует, удаление в Cleanup |
| [0004](0004-self-registration-of-adapters.md) | Адаптеры команд и событий регистрируются сами |
| [0005](0005-targeting-and-effects-in-core.md) | Отбор целей и применение воздействий — в Core |
| [0006](0006-world-rules-in-core.md) | Правила мира из задания — HP со смертью и марш — живут в Core |
| [0007](0007-no-mechanisms-without-consumers.md) | Механизм в Core — только когда у него есть потребитель |
| [0008](0008-whole-scenario-validation.md) | Сценарий проверяется целиком до запуска |
| [0009](0009-tick-limit-and-action-contract.md) | Лимит тиков и проверка контракта `IAction` во время работы |

Правила кодирования (знаковые числа в домене, `uint32_t` только в IO) отдельным ADR не
оформлены: они описаны в ARCHITECTURE.md, п. 2, и SPECIFICATION.md, п. 1.4.

Новое решение — новый файл со следующим номером. Принятое решение не переписывают:
если оно меняется, пишут новый ADR и в старом отмечают, чем он заменён.
