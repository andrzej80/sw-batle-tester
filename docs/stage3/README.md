# Этап 3. Юниты из «Планов на расширения»

Цель — реализовать Башню, Лекаря, Ворона и Мину (README, «Планы на расширения») и этим
проверить главный критерий задания: новые юниты добавляются **без правок Core**.
Механизмы под них уже в Core и покрыты тестами на тестовых юнитах (T04–T07):
`ITargetRule`, теги, `Scheduler`, `requestRemoval`, юнит без `Health` и без `Movement`,
`Effect::Heal`, событие `UnitHealed`.

- Поведение юнитов — [docs/units](../units/README.md), по файлу на юнит.
- Как юниты раскладываются по деталям — ARCHITECTURE.md, п. 5.2; решения по правилам — п. 8.
- Задачи этапов 1–2 и общие правила — [TASKS.md](../../TASKS.md).

Статус: **вопросы С1–С6 согласованы; выполнены T25–T27.**

## Правила этапа

Действуют общие правила из TASKS.md (сборка без предупреждений, clang-tidy,
clang-format, тесты, изменения спецификации с отчётом «уточнения» / «требуют
согласования»). Дополнительно:

- **Core не меняется.** На каждой задаче `git diff main -- src/Core` пуст. Если задача
  упирается в Core, реализация останавливается: архитектура не выдержала, и вопрос
  согласуется отдельно (с записью в ADR или KNOWN_ISSUES).
- **Новые файлы, а не правки.** Каждый юнит — по схеме ARCHITECTURE.md, п. 5.3: DTO команды
  в `IO/Commands`, `Features/Units/X.{hpp,cpp}`, `App/Bindings/XBinding.cpp`, при
  необходимости DTO события и адаптер в `App/Output`. Существующие файлы `src/` меняются
  только там, где задача это прямо называет.
- **Прежнее поведение не меняется.** Эталоны существующих сценариев
  `tests/scenarios/*/expected.*` не правятся.
- **Спецификация юнита — его файл в `docs/units`.** Основная SPECIFICATION.md меняется
  только в общих разделах (Features/Common, вывод), когда задача это называет.
- Способность, которой пользуется один юнит, лежит рядом с ним (`Features/Units/X.cpp`);
  в `Features/Common` её переносят, когда она понадобится второму
  ([src/Features/README.md](../../src/Features/README.md)).
- Новые сценарии с эталонами составляются без случайного выбора: у каждого действия одна
  подходящая цель и одна подходящая клетка ([tests/scenarios/README.md](../../tests/scenarios/README.md)).
- Каждое новое действие тестируется на оба исхода, во втором — `world.activity().changes()`
  не изменился (`FeatureArena`, `tests/Features/FeatureTestHelpers.hpp`).

## Согласованные решения

Формат ввода и вывода для этих юнитов задание не задавало; решения согласованы до начала
реализации и записаны в спецификации юнитов с пометкой «согласовано».

| # | Вопрос | Решение |
|---|---|---|
| С1 | Команды спавна | `SPAWN_TOWER I X Y H P`, `SPAWN_HEALER I X Y H S`, `SPAWN_RAVEN I X Y H A`, `SPAWN_MINE I X Y P`; поля DTO `unitId x y hp power` / `… hp spirit` / `… hp agility` / `unitId x y power` |
| С2 | Тип в `UNIT_SPAWNED` | `Tower`, `Healer`, `Raven`, `Mine` |
| С3 | Событие лечения | `UNIT_HEALED healerUnitId=… targetUnitId=… amount=… targetHp=…`; `amount` — фактически восстановленное HP |
| С4 | Проверка статов | `unit.invalid_stat` для `hp`, `power`, `spirit`, `agility` ≤ 0, все ошибки одним списком; новых кодов нет |
| С5 | Взрыв Мины в выводе | событие фичи `MINE_EXPLODED unitId=…` до ударов взрыва, даже если никого не задело |
| С6 | Ворон против Ворона | Ворон не бьёт Ворона: удар когтем — ближний бой |

## Граф зависимостей

```
T25 Дистанция MeleeAttack ─► T28 Ворон ─┐
T26 Башня ──────────────────────────────┤
T27 Лекарь и UNIT_HEALED ───────────────┼─► T30 Сценарий всех юнитов и документы
T29 Мина ───────────────────────────────┘
```

T25, T26, T27 и T29 независимы и затрагивают разные файлы — их можно делать параллельно
(это и есть проверка «10 разработчиков одновременно»). Взаимодействие новых юнитов между
собой (Башня стреляет в Ворона, Мина взрывает Ворона, Лекарь лечит Ворона) проверяется в
T30, чтобы задачи юнитов не ждали друг друга; внутри своей задачи юнит проверяется на
Мечнике, Охотнике и тестовых юнитах.
