# Деление на задачи

Задачи выведены из [ARCHITECTURE.md](ARCHITECTURE.md) и [SPECIFICATION.md](SPECIFICATION.md).
Ссылки вида «спец. 5.3» — на разделы спецификации.

## Правила для всех задач

- Одна задача — одно изменение, которое можно отдельно проверить на ревью.
- Задача закрыта, когда: код собирается без предупреждений (`-Wall -Wextra -Wpedantic
  -Wconversion -Wsign-conversion`, спец. 11) на clang 15 и clang 18, clang-tidy-18 по
  `.clang-tidy` не даёт замечаний, форматирование соответствует clang-format-18 (как в CI),
  её тесты проходят, все прежние тесты проходят, критерии приёмки из спецификации
  покрыты тестами.
- Задача не трогает файлы вне своего слоя, кроме явно указанных.
- **Изменения спецификации по ходу реализации:**
  1. поведение, коды ошибок, формат вывода, критерии приёмки — если их нужно менять,
     реализация останавливается и вопрос согласуется; в спецификацию правка вносится
     только после согласования;
  2. сигнатуры и внутреннее устройство спецификация описывает как набросок, источник
     правды — код и тесты; в спецификацию такие правки вносятся, только если меняется
     смысл;
  3. отчёт по задаче содержит раздел «Изменения спецификации» с двумя списками:
     «уточнения» (п. 2) и «требуют согласования» (п. 1).
- Размер: **S** — до часа, **M** — 1–3 часа, **L** — больше 3 часов.

## Задачи

### T01. Каркас сборки и тестов — S

- **Сделать:** каталоги по архитектуре (п. 3); CMake-цели `sw_core`, `sw_features`,
  `sw_io` (static), `sw_app` (OBJECT), `sw_battle_test`, `sw_tests`; флаги
  предупреждений; санитайзеры `undefined,implicit-conversion` для `sw_tests`
  (на Ubuntu нужен пакет `libclang-rt-15-dev`, спец. 11);
  комментарий в CMake про запрет static для `sw_app`; проверка границ слоёв
  `cmake/CheckLayerBoundaries.cmake` в каждой сборке (спец. 11);
  `tests/TestFramework.hpp` (`TEST`, `CHECK`, `CHECK_EQ`, `CHECK_THROWS`); `ctest`.
- **Не трогать:** `cmake_minimum_required 3.27`.
- **Готово:** пустой тест проходит в `ctest`; `main` вызывает заглушку `Application::run`.

### T02. Core/Common — S

- **Сделать:** `UnitId`, `Tick`, `Position`, `chebyshev`, `DistanceRange`, `Diagnostic`,
  `Result<T>`, `Result<void>`, `Tag`, `TagSet`, `narrow<T>` (спец. 1).
- **Готово:** приёмка спец. 1.3 и 1.4; тесты на `Result` (доступ к значению при
  ошибке — исключение).

### T03. Core/Events — S

- **Сделать:** `EventBus`, события Core (спец. 2).
- **Зависит от:** T02.
- **Готово:** приёмка спец. 2.

### T04. Core/Units — M

- **Сделать:** `IComponent`, `Unit`, хранилище компонентов с индексом хуков,
  `UnitBlueprint`, `Health`, `Movement`, `Status`, `ComponentRequirements`,
  интерфейсы `ITargetRule`, `IHitModifier` (объявления; спец. 3, 5.1).
- **Зависит от:** T02.
- **Готово:** `get<T>` отсутствующего компонента — исключение; компонент-хук
  попадает в индекс в порядке добавления; приёмка спец. 3.3.

### T05. Core/World — M

- **Сделать:** `Map` (вместе с `IMoveCostModifier`, `IEnterTrigger`), `UnitStore`,
  `SpatialQuery`, `ActivityTracker`, `World` как агрегат (спец. 4); занятость и
  свойства клеток хранятся разреженно.
- **Зависит от:** T04.
- **Готово:** приёмка спец. 4, включая карту `4294967295 × 4294967295`.

### T06. Core/Interaction — M

- **Сделать:** `Intent`, `Effect`, `TargetSpec`, `Hit`, `Targeting`, `Interaction`
  (урон, лечение, смерть с немедленным `UnitDied`, наложение статуса) (спец. 5).
- **Зависит от:** T03, T05.
- **Готово:** приёмка спец. 5.3; тест на правило цели в стиле Ворона: запрет `melee`
  для `Hostile`, лечение проходит; тест на порядок модификаторов.

### T07. Core/Simulation — L

- **Сделать:** `Scheduler`, `TurnContext` с фасадами, `MovementService`, `MarchStep`,
  `Simulation` (три фазы, условия конца, лимит тиков, проверка контракта `IAction`),
  `IRandom`, `StdRandom` (спец. 6).
- **Зависит от:** T06.
- **Готово:** приёмка спец. 6.4; тесты марша: прямой шаг, обход занятой клетки,
  ожидание без свободных клеток, очередь маршей с `MARCH_ENDED` → `MARCH_STARTED`
  в одном тике, юнит без `Movement` не двигается.
- **Можно делить:** T07a `Scheduler` + `TurnContext`, T07b движение и марш,
  T07c `Simulation`.

### T08. Core/Setup — M

- **Сделать:** `SetupContext` со всеми проверками и подавлением ошибок-последствий
  (спец. 7).
- **Зависит от:** T07.
- **Готово:** тест на каждый код ошибки из таблицы спец. 7; спавн с плохими статами
  и занятой клеткой даёт обе ошибки; `MARCH` на отклонённый спавн ошибок не даёт.

### T09. IO/CommandParser — M

- **Сделать:** парсер с номерами строк и `ParseDiagnostic`; строгий разбор `uint32_t`
  без `operator>>` (только цифры + `std::from_chars`); проверка типа поля через
  `static_assert`; проверка числа аргументов (спец. 8). DTO и `EventLog` не меняются.
- **Зависит от:** T01 (с Core не связана — идёт параллельно).
- **Готово:** приёмка спец. 8.

### T10. Features/Common — M

- **Сделать:** `CommonTags`, `TargetSpecs`, `Stats` (включая `Range`), `stat<T>`,
  `distance(min, max)`, `UnitBuilder` с проверкой требований, `MeleeAttack`,
  `RangedAttack`, `RequireNoAdjacentOccupying` (спец. 9.1–9.2).
- **Зависит от:** T07.
- **Готово:** сборка юнита с действием без нужного компонента — исключение с
  понятным текстом; `distance` со `stat<T>` вычисляется при каждом выполнении,
  `min > max` даёт отсутствие целей; тесты действий на тестовом мире.

### T11. Features/Units: Мечник и Охотник — S

- **Сделать:** `SwordsmanSpec`/`makeSwordsman`, `HunterSpec`/`makeHunter` (спец. 9.3).
- **Зависит от:** T10.
- **Готово:** приёмка спец. 9.3; все ошибки статов возвращаются одним списком.
- **Можно делить:** Мечник и Охотник — две независимые подзадачи.

### T12. App/Инфраструктура — M

- **Сделать:** `Registrar` и макросы `SW_REGISTER_BINDING` / `SW_REGISTER_OUTPUT`,
  `CommandRegistry`, `ScenarioLoader`, `DiagnosticPrinter`, `Application` (аргументы,
  коды выхода, перехват исключений) (спец. 10.1–10.3).
- **Зависит от:** T08, T09.
- **Готово:** таблица спец. 10.1 покрыта тестами (кроме нормального запуска —
  он в T16); дубль регистрации команды — код 3.

### T13. App/Output — S

- **Сделать:** `EventBridge`, `CoreEventsOutput`; перевод `int64_t → uint32_t`
  через `narrow` (спец. 10.4, 10.5).
- **Зависит от:** T03, T12.
- **Готово:** каждое событие Core выводится в формате `EventLog`; дубль адаптера —
  исключение; значение вне `uint32_t` — исключение.

### T14. App/Bindings — S

- **Сделать:** `CoreBindings` (`CREATE_MAP`, `MARCH`), `SwordsmanBinding`,
  `HunterBinding` — по одному файлу, с саморегистрацией.
- **Зависит от:** T11, T12.
- **Готово:** адаптеры без логики (только перевод полей `uint32_t → int64_t` и
  `UnitId`, спец. 10.5); команды находятся реестром без общего списка.

### T15. App/Конвейер сценария — M

- **Сделать:** `ScenarioValidator` (проход 1) и `ScenarioRunner` (проход 2 +
  симуляция); подключение в `Application` (спец. 10.2).
- **Зависит от:** T07, T13, T14.
- **Готово:** при ошибках stdout пуст; ошибки идут в порядке строк; у
  `unit.duplicate_id` и `unit.cell_occupied` указана строка спавна связанного юнита.

### T16. Сценарные тесты — M

- **Сделать:** набор сценариев в `tests/scenarios/` с эталонами stdout/stderr и
  кодом выхода; детерминизм через `IRandom`-заглушку.
- **Зависит от:** T15.
- **Сценарии:**
  - `commands_example.txt` — проходит, события в правильном порядке и формате;
  - сценарий со всеми видами ошибок разбора и проверки — полный лог, код 2;
  - пустой файл, нет аргумента, нет файла — коды 1 и 2;
  - бой до одного выжившего; остановка «ничего не произошло»;
  - смерть до своего хода; обход убитого, стоящего на пути;
  - Охотник: выстрел, удар из тени при соседе, бездействие без целей;
  - очередь маршей.

### T17. Документация — S

- **Сделать:** README (сборка, запуск, тесты, как добавить юнит — ссылка на

- **Зависит от:** T16.

## Что не входит

- Башня, Лекарь, Ворон, Мина, статусы и свойства клеток как контент — по заданию
  их не реализуют. Механизмы под них (хуки, `Scheduler`, `Intent`/`Effect`, теги)
  входят в T04–T07 и покрываются тестами на тестовых юнитах внутри тестов.
- `UNIT_HEALED` в IO — вместе с Лекарем.
