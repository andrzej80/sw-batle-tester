`Core` — это расширяемая основа проекта. 
- В будущем только вы несёте полную ответственность за этот код и контролируете все его изменения, предоставляя множеству разработчиков возможность создавать игровые функции в отдельной директории.
- Не станьте узким горлышком в разработке.

## Что относится к Core

Код попадает в Core, только если выполнены **оба** условия:

1. **Это правило мира из задания или механизм, которым пользуется хотя бы один юнит**
   из задания или «Планов на расширения». Правила мира: клетки и их занятость, ход и
   порядок ходов, HP и смерть, марш, конец симуляции.
2. **Фича не может сделать это сама через публичный API Core** — или может, но тогда
   правило можно было бы обойти. Пример: правила цели Ворона проверяет `Targeting` в
   Core, поэтому ни одно новое действие их не забудет.

**Признак ошибки:** в Core появилось имя конкретного юнита, характеристика фичи
(`Strength`, `Agility`, `Range`), конкретное действие (удар, выстрел) или игровое число
(радиус 2, дальность 5). HP и марш ошибкой не считаются: это правила мира
([ADR 0006](../../docs/adr/0006-world-rules-in-core.md)).

**Механизм без потребителя в Core не держим**
([ADR 0007](../../docs/adr/0007-no-mechanisms-without-consumers.md)). Модификаторы
удара, свойства клеток и стаки статусов были в Core «на вырост» и удалены: им не
нашлось ни одного юнита. Как вернуть каждый, когда юнит появится, — KNOWN_ISSUES.md,
п. 12.

**Механизм сначала живёт в фичах.** Если что-то можно сделать через публичный API
Core, это делают в Features. В Core механизм переносят, когда им пользуются несколько
фич и его нельзя давать обходить. Перенос из Features в Core дешёвый, обратный —
дорогой: к тому времени от интерфейса Core зависят все фичи.

## Что сейчас в Core

| Часть | Что внутри |
|---|---|
| пространство | `Map` (размер, разреженная занятость клеток), `SpatialQuery`, `MovementService::stepTo` |
| юниты | `Unit`, `ComponentStore`, компоненты Core: `Health`, `Movement`, `Status` |
| время | три фазы тика, порядок ходов, одно действие за ход, `Scheduler`, конец симуляции, лимит тиков |
| марш | очередь маршей, `MarchStep`, события `MARCH_*` |
| воздействия | `TargetSpec` (`Intent`, `Effect`, теги, дистанция), `Targeting`, `Interaction`, `ITargetRule` |
| инфраструктура | `IAction`, `TurnContext`, `EventBus`, `IRandom`, `Result`/`Diagnostic`, `SetupContext` |

Закрыто намеренно — это ядро правил, а не точки расширения: три фазы тика, условия
конца, набор событий Core, флаг `occupiesCell`, оси `Intent` и `Effect`.

## Как предложить изменение Core

1. Назвать потребителя: юнит из задания или «Планов», которому это нужно.
2. Показать, почему не получается через публичный API Core, или какое правило иначе
   можно обойти.
3. Приложить тест на тестовом юните (`tests/Core`) и обновить спецификацию.
   Изменение поведения, кодов ошибок или формата вывода согласуется до правки
   SPECIFICATION.md.

Контракты интерфейсов, которые охраняет владелец Core, — ARCHITECTURE.md, п. 4.13.
Core не включает ни `Features`, ни `IO`, ни `App`; это проверяет сборка
(`cmake/CheckLayerBoundaries.cmake`).
