`Feature` — это директория для реализации игровых фичей.
- Здесь разработчики размещают код юнитов и их поведение, используя возможности, предоставленные `Core`.

---

## Как устроены Features

| Каталог | Что внутри |
|---|---|
| `Common/` | то, чем пользуются разные юниты: базовые теги (`CommonTags`), конструкторы воздействий (`TargetSpecs`: `attack`, `heal`, `buff`, `debuff`), статы (`Stats`), источники чисел (`ValueSource`: `stat<T>`, `distance(min, max)`), сборщик юнита (`UnitBuilder`), действия `MeleeAttack` и `RangedAttack` |
| `Units/` | юниты: спецификация (`HunterSpec`), проверка характеристик и сборка из готовых деталей. Своей логики поведения здесь нет |

Новая способность — новый класс действия. Пока ею пользуется один юнит, она может
лежать рядом с ним. В `Common/` её переносят, когда она понадобилась второму юниту.

**Новый вариант способности — параметр, а не флаг.** Урон задаёт `ValueSource`
(число или `stat<T>`), дистанцию — `distance(min, max)`, условие выстрела — отдельный
объект-условие (`RequireNoAdjacentOccupying`). Если ради одного юнита хочется добавить
в действие `bool`, лучше написать отдельное действие.

## Контракт действия (`IAction`)

- `tryExecute` вернул `false` — действие неприменимо: оно **не вызывало** изменяющих
  методов `TurnContext` (урон, шаг, событие, отложенный эффект). Это проверяется во
  время работы: нарушение — `std::logic_error` с именем действия
  ([ADR 0009](../../docs/adr/0009-tick-limit-and-action-contract.md)).
- `tryExecute` вернул `true` — действие выполнено, ход юнита закончен, даже если эффект
  равен 0.
- `requirements` перечисляет **все** компоненты, которые действие читает у `self`:
  юнит без них не соберётся. `stat<T>` объявляет свой компонент сам.
- Состояние действия (например, «мина взведена») хранится в самом объекте действия:
  у каждого юнита свои экземпляры. Действие, которое поменяло своё состояние, обязано
  вернуть `true`: такое изменение счётчик Core не видит, и нарушение контракта прошло бы
  незаметно (KNOWN_ISSUES.md, п. 8).
- Цели выбирают только через `context.targeting()`, применяют воздействие — через
  `context.effects()`. Обойти правила цели нельзя: `Hit` мимо отбора — `logic_error`.

**У каждого действия должен быть тест на оба исхода:** когда оно выполняется и когда
неприменимо. Во втором случае проверить, что `world.activity().changes()` не
изменился. Тестовый мир с настоящими юнитами — `FeatureArena` в
`tests/Features/FeatureTestHelpers.hpp`.

## Правила зависимостей

- Features включают только Core. `IO` и `App` включать нельзя: сборка упадёт со списком
  нарушений (`cmake/CheckLayerBoundaries.cmake`).
- `Units/` → `Common/` → Core. `Common/` не зависит от `Units/`.
- Фича не знает формат ввода: параметры юнита она описывает своей спецификацией
  (`HunterSpec` с полями `int64_t`) и возвращает ошибки без номеров строк.

## Теги

Тег объявляется по имени: `inline const core::Tag Fire{"fire"};`. Одинаковое имя в
разных фичах — один и тот же тег. Базовые теги (`melee`, `ranged`, `area`, `physical`,
`flying`) лежат в `Common/CommonTags`. Тег конкретной механики объявляют в файле фичи,
которой он нужен. Перед тем как завести новый, проверьте, нет ли такого имени с другим
смыслом (KNOWN_ISSUES.md, п. 9).

## Как добавить юнит

1. `src/IO/Commands/SpawnX.hpp` — DTO команды (формат ввода).
2. `src/Features/Units/X.{hpp,cpp}` — `XSpec`, проверка характеристик (все ошибки сразу,
   `requirePositive`) и сборка через `UnitBuilder` из готовых деталей.
3. `src/App/Bindings/XBinding.cpp` — перевод `io::SpawnX` в `XSpec` и
   `SW_REGISTER_BINDING` в конце файла.
4. Если нужен новый вид события в выводе — DTO в `src/IO/Events` и адаптер
   `src/App/Output/XEventOutput.cpp` с `SW_REGISTER_OUTPUT`.
5. Тесты: сборка и проверка характеристик (`tests/Features/Units`), сценарий с
   эталоном (`tests/scenarios/<имя>`).

Core и общие файлы при этом не меняются. Как ложатся юниты из «Планов» (Башня, Лекарь,
Ворон, Мина) — ARCHITECTURE.md, п. 5.2.
